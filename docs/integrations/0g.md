# Tribunal × 0G

Tribunal is a verifiable AI court for autonomous agents. When two agents transact and disagree, Tribunal runs the dispute as a real trial (lawyers, clerk, judge panel) and produces a binding, verifiable ruling that releases or claws back escrow automatically. 0G is the spine of the system: every contract, every iNFT judge, and every byte of the audit trail lives on 0G.

### 2. Judges as ERC-7857 iNFTs

Each judge is minted as an ERC-7857 iNFT in [`contracts/src/JudgeINFT.sol`](../../contracts/src/JudgeINFT.sol). Two non-trivial pieces of state ride along with the token:

- **Encrypted persona** stored via `metadataRoot` — see [`JudgeINFT.sol:39`](../../contracts/src/JudgeINFT.sol#L39). The judge's prompt, persona, and configuration are stored encrypted; only the enclave can decrypt and run them.
- **Evolving precedent memory** appended via `appendRulingMemory` — see [`JudgeINFT.sol:43`](../../contracts/src/JudgeINFT.sol#L43). Every ruling the judge issues appends a content hash to the iNFT's on-chain memory log.

The full call chain that fires `appendRulingMemory` after every verdict:

- [`agents/src/roles/judge.ts:166`](../../agents/src/roles/judge.ts#L166) — at the tail of the judge role's deliberation loop, immediately after `submitRuling` lands: `await a.tribunal.appendJudgeMemory(a.tokenId, opinionHash);`.
- [`agents/src/chain/tribunal-client.ts:88`](../../agents/src/chain/tribunal-client.ts#L88) — `appendJudgeMemory` wrapper.
- [`agents/src/chain/tribunal-client.ts:89`](../../agents/src/chain/tribunal-client.ts#L89) — actual on-chain call: `await deps.judgeINFT.appendRulingMemory(tokenId, h)`.
- [`agents/src/chain/tribunal-client.ts:31`](../../agents/src/chain/tribunal-client.ts#L31) — typed `appendRulingMemory` interface on the `judgeINFT` dependency.
- [`agents/src/runner.ts:267`](../../agents/src/runner.ts#L267) — runner constructs a judge-bound contract handle (signed with `judgeWallet`) so the on-chain `ownerOf()` check inside `appendRulingMemory` passes.
- [`agents/src/runner.ts:325`](../../agents/src/runner.ts#L325) — comment confirming the same constraint: "because appendRulingMemory checks ownerOf()."
- [`agents/src/demo.ts:155`](../../agents/src/demo.ts#L155) — demo asserts the iNFT's `rulingHistory(judgeTokenId)` length grows by one per case.
- [`agents/src/demo.ts:352`](../../agents/src/demo.ts#L352) — demo reads `rulingHistory` back at the end and asserts the new entry equals the case-ruling hash.
- [`agents/tests/chain/tribunal-client.test.ts:31`](../../agents/tests/chain/tribunal-client.test.ts#L31) — unit test "appends judge memory via JudgeINFT.appendRulingMemory".

The judge iNFT is the judge's identity, persona, and reputation in a single transferable artifact. A judge with a bad track record is publicly visible to anyone empanelling them.

### 3. Content-addressed audit trail on 0G Storage

Every single response received over AXL (case filings, evidence, lawyer arguments, judge deliberations, REE receipts) is uploaded to 0G Storage. Each upload's content hash is anchored on-chain via `TribunalCore.recordEvent`. The full proceeding is replayable from chain data alone, and tampering is detectable because the on-chain hash will not match.

**0G Storage SDK wrapper:**

- [`agents/src/storage/og-storage.ts`](../../agents/src/storage/og-storage.ts) — wraps the 0G Storage SDK behind a small `ZgStorage` interface so consumers do not depend on SDK details.
- [`agents/src/storage/og-storage.ts:30`](../../agents/src/storage/og-storage.ts#L30) — `contentHash(bytes)` pure helper, used everywhere we need the on-chain anchor for an event before upload completes.
- [`agents/src/storage/og-storage.ts:60`](../../agents/src/storage/og-storage.ts#L60) — Galileo `Flow.Submit` event topic hash, used to recover the storage root from the upload tx receipt.
- [`agents/src/storage/og-storage.ts:85`](../../agents/src/storage/og-storage.ts#L85) — actual `indexer.upload(file, rpcUrl, signer)` call into the 0G Storage SDK.

**On-chain anchoring path (`recordEvent`):**

- [`contracts/src/TribunalCore.sol:90`](../../contracts/src/TribunalCore.sol#L90) — `recordEvent(caseId, contentHash)` (only the runner can call).
- [`agents/src/chain/tribunal-client.ts:9`](../../agents/src/chain/tribunal-client.ts#L9) — typed `recordEvent` dependency on the `tribunalCore` contract.
- [`agents/src/chain/tribunal-client.ts:43`](../../agents/src/chain/tribunal-client.ts#L43) — `anchorEvent(caseId, contentHash)` is the public surface the clerk calls.
- [`agents/src/chain/tribunal-client.ts:75`](../../agents/src/chain/tribunal-client.ts#L75) — implementation: `await deps.tribunalCore.recordEvent(caseId, h)`.

**Per-event anchoring inside the clerk:**

- [`agents/src/case/transcript.ts:40`](../../agents/src/case/transcript.ts#L40) — every transcript event computes its `contentHash` via `keccak256(toUtf8Bytes(payload))` at append time; the hash and the bytes travel together.
- [`agents/src/roles/clerk.ts:38`](../../agents/src/roles/clerk.ts#L38) — clerk doc comment: "persists every incoming AXL message as a Transcript event, uploads the canonical JSON to 0G Storage, anchors its content hash on TribunalCore via recordEvent."
- [`agents/src/roles/clerk.ts:60`](../../agents/src/roles/clerk.ts#L60) — clerk encodes the event JSON: `const blob = new TextEncoder().encode(JSON.stringify(ev));`.
- [`agents/src/roles/clerk.ts:63`](../../agents/src/roles/clerk.ts#L63) — uploads to 0G Storage: `const up = await deps.storage.upload(blob);`.
- [`agents/src/roles/clerk.ts:64`](../../agents/src/roles/clerk.ts#L64) — anchors the content hash on `TribunalCore`: `const anchor = await deps.tribunal.anchorEvent(deps.caseId, ev.contentHash);`.
- [`agents/src/roles/clerk.ts:50`](../../agents/src/roles/clerk.ts#L50) — anchor txs are serialised through a per-clerk promise chain (`anchorChain`) so the operator wallet's nonce sequencing does not race when two AXL events arrive milliseconds apart.

### 4. Multi-agent swarm coordinating on 0G

Four independent agents run the trial: **clerk, lawyer-A, lawyer-B, judge**. They coordinate without any centralised broker, each owning a distinct role:

- [`agents/src/roles/clerk.ts`](../../agents/src/roles/clerk.ts) — opens the docket and routes filings, evidence, arguments, and rulings.
- [`agents/src/roles/lawyer.ts`](../../agents/src/roles/lawyer.ts) — gathers evidence, drafts pleadings, and streams arguments on behalf of one party.
- [`agents/src/roles/judge.ts`](../../agents/src/roles/judge.ts) — deliberates inside a Gensyn REE enclave, looks up rulebook articles, casts votes.
- [`agents/src/roles/party.ts`](../../agents/src/roles/party.ts) — the litigant agent.

The end-to-end trial driver is [`agents/src/runner.ts`](../../agents/src/runner.ts); the demo orchestration is [`agents/src/demo.ts`](../../agents/src/demo.ts).

When a quorum of judges agrees, [`TribunalCore.submitRuling`](../../contracts/src/TribunalCore.sol#L97) finalises the verdict, [`VerdictLog.post`](../../contracts/src/VerdictLog.sol) records it, and [`EscrowAdapter`](../../contracts/src/EscrowAdapter.sol) releases or claws back the disputed funds. No human in the loop.

### 5. ENS-anchored rulebook stored as 0G + ENS hybrid

[`contracts/src/RuleBook.sol`](../../contracts/src/RuleBook.sol) stores only `(articleId, ensNode, chapter)` tuples on 0G — see the `Article` struct at [`RuleBook.sol:17`](../../contracts/src/RuleBook.sol#L17) and the `addArticle` writer at [`RuleBook.sol:44`](../../contracts/src/RuleBook.sol#L44). Each article's title and body lives as ENS text records on `chapter-X-Y.rulebook.tribunal.eth` subnames, resolved at deliberation time by [`agents/src/judge/ens-resolver.ts:71`](../../agents/src/judge/ens-resolver.ts#L71) (`chapterEnsNode`). See the seeder at [`scripts/seed-rulebook-ens.ts`](../../scripts/seed-rulebook-ens.ts) and the rulebook record at [`docs/rulebook-deployment.json`](../rulebook-deployment.json).

This pattern (cheap on-chain pointer + offchain rich content) leans on 0G as the canonical source of truth for _what is binding_ while keeping the rulebook openly amendable through `RuleBookGovernor`.

### 6. REE receipts anchored on 0G

Every judge inference produces a Gensyn REE receipt; the receipt's hash and URL are pinned on-chain via `VerdictLog.attachReceipt`:

- [`contracts/src/VerdictLog.sol:49`](../../contracts/src/VerdictLog.sol#L49) — `attachReceipt(caseId, receiptHash, receiptUrl)` writes the receipt and emits `VerdictReceiptAttached`.
- [`contracts/src/VerdictLog.sol:21`](../../contracts/src/VerdictLog.sol#L21) — `Receipt` struct.
- The agent-side smoke test driving the on-chain receipt anchor is [`scripts/ree-onchain-smoke.ts`](../../scripts/ree-onchain-smoke.ts).

This gives 0G a verifiable inference primitive: anyone can re-run the receipt in REE's verify mode and confirm the verdict text was actually produced by the claimed model on the claimed inputs.
